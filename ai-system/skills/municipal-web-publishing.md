# PTA自治体総評 Web制作・公開・検証スキル v1.0.0

## 責務と依存
- **調査・法的評価の正本**は `ai-system/skills/municipal-assessment-v3.md`。本スキルは評価済み事実・レビュー状況から、公開サイトを構築・検証する「制作から実公開まで」の実行工程を規定する。調査の未完了を、見栄えのよいページで隠さない。
- 変更・公開は `AGENTS.md` の副作用承認を優先する。承認がない場合はPRや未公開草稿までに留める。
- 既存サイトの `website-article`、`website-edit`、`publish-verification` の技能を利用し、各ページに別々の例外CSSを積み重ねることを標準にしない。

## 1. 作業開始時の現状調査
1. 対象自治体・年度・公開URL・現在の表示・地図の接続先を確定。
2. **対象ファイル、修正方針、変更しない範囲**を必ず宣言。基準ブランチとコミットSHAを記録。
3. 対象ページのHTML・スタイルシート・JavaScript・JSON・生成スクリプトの**生成元と依存関係を追跡**。共通CSS・ページ固有CSS・インラインstyle・JS動的DOMのどれが最終表示を決めているかを確認する。生成物の手修正だけで済ませない。
4. 既存の本文、引用、学校名、学校別原資料、id属性、canonical、JSON-LD、PDF URL、全国地図のピンと索引をバックアップ／差分基準として固定。
5. 調査・法的総評が確定済みか、暫定かを確認。未確認の自治体規程や法令違反をサイトの「確定」ラベルとして掲載しない。

## 2. 公開用データと記事の設計
1. **階層固定：全国地図→自治体総評→学校別評価→原資料。** 地図に掲載しただけで学校ページ作成済みとしない。
2. 市の制度責任、学校・PTAの具体的行為、保護者・児童の権利を別段落で記す。行政の改善を時系列で肯定的に評価し、方針・通知・実行・効果確認を分ける。
3. 委任・準委任は当事者間の**私法上の契約**で、公法上の学校事務権限をそれ自体では創設しない。本人同意・委託契約による学校徴収正当化条項は自治体側の制定責任として明示し、私法効果・公的権限・個情法61・69・服務・資金保管を分離。
4. 保護者のために見出し・地域固有の課題・改善要求を先に配置する。機械的な一覧・12軸・法律表だけで本文を置換しない。元の詳細な根拠・原文を削除せず下層の詳説へ。
5. 学校名、証拠画像、資料の日付・ページ、引用文字列とリンク先の一致を確認。画像の個人情報・QR・印影・口座をマスキングし、実資料でない再構成図はその旨を表示。
6. 未評価校・資料未開示校・是正計画中を適正済みと表示しない。公開日と原資料日を混同しない。

## 3. CSS／レイアウトの再発防止（必須）
- **根本原因を探す**。画面の右側余白なら、pのmax-widthだけでなく親の `grid-template-columns`、`width`、`max-width`、`min-width`、共通 `.container`、固定サイドバー、インラインstyle、JSで付加されるclass、メディアクエリまでcomputed styleとDOMを確認する。
- 無条件の `width:100%`、`!important`、末尾上書きを連続追加して修復済みとはしない。不要になった旧定義や競合ルールを整理し、意図的に必要な読みやすい文字幅と、誤った空白・グリッドの余りを区別する。
- 日本地図、右側の自治体リスト、カード、長い学校名は **位置・可読性・対比・折り返し・重なり** を同時に確認。文字が背景に沈む、カードが切れる、画面外にはみ出す、学校名が省略されすぎる状態を不合格とする。
- 実表示で **320px／375px／768px／1280px／1440px** を原則確認。本文・見出し・原資料画像・テーブル・地図・学校カードの横方向スクロール、重なり、余分な余白、可読性を検査。PC幅で左右を不自然に詰めない。
- 変更対象外のトップ・地図・他の自治体・学校別ページに回帰がないか確認。共通CSS変更時は **全ページの代表画面** を複数幅で検証。
- screenshotだけでなくComputed StyleとBoundingBoxを確認し、想定コンテナ幅とのずれを記録。ブラウザ実測できなかったら表示確認は未完了。

## 4. OGP・Xカードの再発防止
- 公開ページの初期HTMLの `title`、description、canonical、`og:title`、`og:description`、`og:type`、`og:image`、`twitter:card=summary_large_image` と適切な `twitter:image` を確認。JSで後から設定するだけでは不可。
- OG画像は**公開のHTTPS絶対URL**、HTTP 200、画像Content-Type、有効な実画像（目安1200×630）、robotsの許可を確認。GitHub内に画像があるだけでは不可。相対URLや破損した画像では合格しない。
- Xカードキャッシュを考慮し、画像内容を更新した場合はキャッシュ識別子等を管理。OG画像URLを無意味に毎回更新しない。既存投稿のカードと新規投稿のカードの違いを明記。
- **公開ページのメタタグ → クローラーから取得可能な画像 → Xの投稿画面でのカード実表示** を別々に記録する。Xプレビューを確認できなければ「Xカード設定済み・実表示未確認」で停止。画像生成や画像差替は事実・引用の扱いを確認して実施。
- SNSでURL末尾に付いた `utm_source` 等のパラメータをcanonicalと混同しない。

## 5. GitHub・公開の手順（承認ゲート）
1. 変更前の元コード・生成元・変更範囲を把握。少数ファイルで実装し、文言、データ、CSS、キャッシュ更新を可能な限り切り分ける。
2. 静的検査：`npm test`、`git diff --check`、`git diff --stat`、対象URLのリンク・アンカー・参照ファイル・OGPを検査する。共通ヘッダー生成スクリプト等の `--check` も利用。
3. **デプロイ承認と実行を区別**。commit／push／merge／Pages反映をそれぞれ独立した操作として記録。変更の指示・人間承認がない公開操作はしない。
4. デプロイ後に公開URLをブラウザで開き直し、公開HTML／CSS／画像が新しいバージョンになったことと、JS実行結果が期待通りであることを確かめる。旧キャッシュからの表示を最新版と誤認しない。
5. 公開URLから全国地図→自治体→学校→原資料と辿る。リンク切れ、見出しの埋没、反応しないボタン・地図・検索、重複した評価、学校リンクの欠落を検査。
6. 修復不能・公開待ち・X未確認・人間レビュー未了等は、終了時に**未完了の具体的な検査項目**として報告し、「完成」と宣言しない。

## 6. 公開ゲートと記録
- 静的サイトの確認器 `scripts/validate-municipal-web.mjs`：対象HTMLのcanonical・OGP・SNS・参照URL等を検査し、報告を機械生成。**実ブラウザ確認・外部HTTP確認は別ゲート**。
- 公開チェックマニフェストには、調査レビュー、法的レビュー、元資料保全、生成元同期、地図と学校リンク、静的検証、PC/スマホ実ブラウザ、実公開URL、OG画像HTTP、Xプレビュー、レビュー承認を持つ。未実施を `true` にしない。
- 三つの状態：`draft`（編集途中）、`published_unverified`（GitHubと公開は進んだが検証未了）、`verified`（ブラウザ・根拠・X等の実証まで記録）。法的審査自体の完了状態とは別に保持。
- 結果には更新ファイル・コミット・URL・検査日時・実測した画面幅・スクリーンショット・不足項目を記録。ユーザーが画像で不具合を指摘した際は、**根本原因が特定できるまで「修正済み」と言わない**。
